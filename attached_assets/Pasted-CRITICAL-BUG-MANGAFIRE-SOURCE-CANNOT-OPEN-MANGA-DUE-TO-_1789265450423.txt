CRITICAL BUG — MANGAFIRE SOURCE CANNOT OPEN MANGA DUE TO HUMAN VERIFICATION / ANTI-BOT CHALLENGE

MangaFire currently appears in the source list and manga listings can be displayed, but opening an individual manga frequently fails.

Current behavior:

1. User selects MangaFire.
2. Manga/manhwa listings appear correctly.
3. User taps a manga/manhwa.
4. The app receives a verification / anti-bot / challenge response instead of the manga details/chapter data.
5. The app tells the user to go to the MangaFire website for verification.
6. Opening the website externally does NOT properly solve the problem for the app.
7. The expected verification flow does not appear inside the app.
8. After visiting the website, the user still cannot open the manga inside MangaVerse.
9. Therefore MangaFire manga are effectively unusable.

This must be fixed at the architecture level.

IMPORTANT:
DO NOT attempt to bypass, defeat, automate, or circumvent MangaFire/Cloudflare anti-bot protection.

The correct solution is to provide a legitimate browser/WebView verification flow when the source requires human verification, preserve the resulting session where technically and legally possible, then retry the original request.

PHASE 2 — DISTINGUISH NORMAL ERRORS FROM VERIFICATION
==================================================

The MangaFire adapter must distinguish:

A. Manga not found
B. Network failure
C. Server error
D. Rate limiting
E. Cloudflare/anti-bot challenge
F. JavaScript/browser verification page
G. Unexpected HTML response
H. Actual MangaFire content

Do not treat every HTML response as a generic "verification required" error.

Inspect:

- HTTP status
- final URL after redirects
- response Content-Type
- recognizable challenge markers
- MangaFire page markers
- Cloudflare challenge markers
- challenge URLs
- response body characteristics

Create a clean internal result such as:

VerificationRequired

instead of throwing a generic exception.

==================================================
PHASE 3 — CREATE A REAL IN-APP VERIFICATION FLOW
==================================================

When MangaFire requires human verification, DO NOT simply tell the user:

"Go to MangaFire website."

Instead:

Open a dedicated in-app verification screen/modal using the project's existing supported browser/WebView architecture.

The flow should conceptually be:

User taps Manga
        ↓
MangaFire request
        ↓
VerificationRequired detected
        ↓
Open MangaFire verification page
        ↓
User completes the legitimate verification if required
        ↓
Verification succeeds
        ↓
Return to MangaVerse
        ↓
Retry the original manga request
        ↓
Open manga details normally

The verification UI should clearly tell the user:

"MangaFire requires a quick browser verification before this manga can be opened."

Provide:

- verification WebView/browser area
- loading indicator
- close/cancel button
- retry button if necessary
- clear status
- automatic detection of successful navigation when possible
- return to the original manga after verification

Do not require the user to manually leave the application.

==================================================
PHASE 5 — SESSION / COOKIE HANDLING
==================================================

Investigate whether the verification session established in the WebView can legitimately be reused by the MangaFire HTTP client.

The important problem is:

WebView/browser session
≠
API HTTP client session

If the project architecture permits safe and supported cookie sharing, synchronize the relevant MangaFire session state so that subsequent requests use the same authenticated/verified browser session.

Do NOT copy arbitrary cookies into unrelated domains.

Do NOT expose cookies to logs.

Do NOT store sensitive session data insecurely.

Do NOT assume a Cloudflare clearance cookie can simply be copied between different devices or environments.

If cookie sharing is not reliable/supported by the current architecture, use the verified browser/WebView session for the MangaFire requests that require browser context rather than pretending the HTTP client has been verified.

The important requirement is:

verification must actually affect the subsequent MangaFire request path.

==================================================
PHASE 6 — DO NOT CLOSE THE VERIFICATION TOO EARLY
==================================================

A major possible bug is that the app opens the verification page and immediately closes it or considers verification complete before the challenge actually succeeds.

Do NOT use:

- arbitrary timers
- "wait 3 seconds"
- assume navigation = verification success
- assume HTTP 200 = verification success

Determine successful verification using a reliable signal available to the browser/session.

Only then:

1. close verification UI
2. retry the original request

If verification fails:

- keep the verification UI visible
- explain that verification has not completed
- provide Retry
- do not silently fail

==================================================
PHASE 7 — RETRY THE ORIGINAL MANGA REQUEST
==================================================

The user should NOT have to manually search for the manga again.

Preserve the original request context:

- source ID
- manga ID
- manga URL
- title
- route
- query parameters if needed

Flow:

open manga
→ challenge
→ verify
→ return
→ automatically retry exact manga request
→ display manga details

Prevent duplicate concurrent retries.

Use a clear state machine such as:

idle
→ requesting
→ verificationRequired
→ verifying
→ verified
→ retrying
→ success

or the equivalent architecture already used by the project.

==================================================
PHASE 8 — HANDLE VERIFICATION LOOPS
==================================================

If verification repeatedly returns another challenge:

DO NOT create an infinite retry loop.

For example:

request
→ challenge
→ verify
→ request
→ challenge
→ verify
→ request
→ challenge

must eventually stop and show:

"MangaFire verification could not be completed in this environment."

Provide:

- Retry verification
- Open in system browser
- Cancel

The app must not continuously reload the page.

Cloudflare documentation notes that challenge loops can be caused by browser configuration, JavaScript, unsupported/embedded browser environments, network conditions, or bot-detection signals. Therefore diagnose the actual WebView environment instead of adding arbitrary retries.

==================================================
PHASE 9 — SYSTEM BROWSER FALLBACK
==================================================

If the current Android WebView cannot reliably complete MangaFire verification, provide a proper fallback:

"Open in browser"

This should open the exact MangaFire verification/manga URL in the system browser.

After the user returns to MangaVerse, the app should clearly determine whether it can continue using the verified session.

Do NOT falsely tell the user verification succeeded if the app cannot access the resulting browser session.

If system-browser verification cannot be shared with the app's HTTP client, explain this clearly and keep the MangaFire browser fallback available.
