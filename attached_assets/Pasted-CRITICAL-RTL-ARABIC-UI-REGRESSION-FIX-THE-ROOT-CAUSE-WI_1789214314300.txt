CRITICAL RTL / ARABIC UI REGRESSION — FIX THE ROOT CAUSE WITHOUT DESTROYING THE ORIGINAL DESIGN

The internationalization system is now implemented, but there is a serious visual regression when switching the application language to Arabic.

CURRENT PROBLEM:

When the user changes the application language to Arabic:

1. Many icons become visually incorrect or "scrambled".
2. Some icons are mirrored when they should NOT be mirrored.
3. Some directional icons may be mirrored incorrectly.
4. Several UI layouts no longer match their original design.
5. Spacing/alignment/order of elements changes incorrectly.
6. Some screens no longer preserve the original visual structure.
7. The English/LTR version has the intended original design, but Arabic/RTL causes parts of the UI to become distorted.

DO NOT treat this as a simple "set everything to RTL" problem.

The goal is:

Arabic text + correct RTL behavior + preserved original visual design.

==================================================
PHASE 1 — STOP BLIND RTL PATCHING
==================================================

Before changing code, inspect the CURRENT i18n and RTL implementation.

Determine exactly how RTL is currently being applied.

Search for:

- I18nManager
- forceRTL
- allowRTL
- isRTL
- direction
- writingDirection
- flexDirection
- row-reverse
- scaleX(-1)
- transform
- mirrored
- RTL providers
- direction context
- locale providers
- layout direction helpers
- icon mirroring logic
- navigation direction logic.

Also inspect every recent change related to the i18n implementation.

Do not assume the current RTL implementation is correct.

Find the exact architectural reason why switching to Arabic changes the visual structure incorrectly.

==================================================
PHASE 2 — PRESERVE THE ORIGINAL DESIGN
==================================================

The existing LTR design is the visual reference.

IMPORTANT:

Do NOT redesign the application.

Do NOT change:

- colors
- typography unnecessarily
- spacing unnecessarily
- card sizes
- button sizes
- component hierarchy
- visual style
- screen structure
- reader design
- navigation design
- animations.

The objective is NOT to create a new Arabic design.

The objective is to make the EXISTING design work correctly in RTL.

Think of it as:

Original UI
      +
Correct RTL behavior
      =
Same visual quality in Arabic

==================================================
PHASE 3 — CORRECT RTL ARCHITECTURE
==================================================

Separate these concepts:

1. TEXT DIRECTION
2. LAYOUT DIRECTION
3. ICON DIRECTION
4. NAVIGATION DIRECTION
5. CONTENT ORDER.

They must NOT all be handled by blindly applying row-reverse or mirroring everything.

Implement RTL at the correct architectural level.

Use the framework's recommended RTL mechanism.

Do NOT manually add `flexDirection: row-reverse` to every component unless that component genuinely requires it.

Do NOT globally reverse every row.

Do NOT globally mirror every image/icon.

==================================================
PHASE 4 — ICON MIRRORING MUST BE SELECTIVE
==================================================

This is extremely important.

Do NOT mirror all icons when Arabic is selected.

Create a clear distinction between:

A) Directional icons

These may need RTL-aware behavior:

- back
- forward
- next
- previous
- left arrow
- right arrow
- chevron left
- chevron right
- navigation arrows.

B) Non-directional icons

These should generally NOT be mirrored:

- search
- settings
- heart
- bookmark
- download
- upload
- translate
- language
- information
- notification
- profile
- home
- menu
- edit
- delete
- refresh
- filter
- camera
- image
- play
- pause
- volume
- theme icons
- generic action icons.

C) Icons whose visual meaning is orientation-specific

These must be evaluated individually.

Do NOT use a global:

transform: [{ scaleX: -1 }]

for all icons.

If there is currently a global icon-mirroring mechanism, identify it and replace it with a semantic/directional approach.

==================================================
PHASE 5 — DO NOT MIRROR UI ELEMENTS THAT SHOULD REMAIN VISUALLY STABLE
==================================================

Some UI components should preserve their visual orientation even when the surrounding layout becomes RTL.

Examples may include:

- logos
- brand marks
- artwork
- manga/manhwa images
- character images
- decorative graphics
- progress indicators where direction has semantic meaning
- media controls
- custom illustrations.

Do not automatically mirror these.

==================================================
PHASE 6 — FIX FLEXBOX / LAYOUT DIRECTION
==================================================

Audit components that currently depend on:

- flexDirection
- justifyContent
- alignItems
- position
- left/right
- marginLeft/marginRight
- paddingLeft/paddingRight
- borderLeft/borderRight.

Determine which values should become RTL-aware and which must remain physically anchored.

Do NOT blindly replace:

left → right
right → left

throughout the project.

Use logical layout concepts where supported.

For example, distinguish between:

- logical "start/end"
and
- physical "left/right".

Some controls are semantically tied to the physical side of the screen and should not be reversed.
